# Log: boot-word discard resolved from the sample corpus; core-vs-wrapper source boundary identified

Two Eli observations drove this: (1) the old samples mostly start with NOPs,
which might be *why* the first-instruction-discarded claim is true; (2) for the
EZHB_EMER_SEL polarity question, prefer the original .docx architecture document
over AN14650.

## 1. Boot-word discard - now effectively settled

Surveyed every EZH program in the historical corpus (C:\eli\ezh, 116 function
bodies). First pass was wrong: a naive regex read instructions out of Keil
`MACRO`/`MEND` definition blocks and C `#define` bodies, reporting only 61/116
NOP openers. After stripping those:

- **97** open with a literal `E_NOP`
- **14** open with `MIPIDMA_PROLOGE`, whose first instruction is `E_NOP`
- **2** are `EZH_MACROS` pseudo-functions (pure macro containers, not programs)
- **2** = `EZH_RegistersDump` - a breakpoint **vector target**, not a boot entry
- **1** = `hello_pdm.c` (see below)

So **111 of 114 real programs open with E_NOP**, and the exceptions are exactly
the cases the rule predicts: entry points reached by branch/vector/breakpoint
substitution lose nothing and need no NOP. AN14650 §4.2.12 shows both halves of
that pair in one example - its boot routine `EZH_SetRegisters` opens with
`E_NOP`, its breakpoint handler `EZH_RegistersDump` opens straight into
`E_PUSH(R4)`.

**The decisive case is hello_pdm.** Its boot entry `ezh_pdm` (booted directly:
the deck shows `EZH_Boot(ezh_pdm, &para, 0)`) places `E_DCD(envelope_buffer)` -
a *data constant* - in the boot word, and branches from the second word with
`E_ADD_IMM(PC,PC,4*4)`. If the boot word were executed, the program would
execute a RAM pointer as an instruction. It works. A NOP opener is compatible
with both hypotheses; a data word is only compatible with "discarded".

Evidence now stands at four independent directions: deck statement, behavioral
model (`PC_manager = new(boot_addr + 4, ...)`), 111/114 corpus convention, and
the hello_pdm data-in-boot-word proof. Chapter upgraded from a hedge blockquote
to a full subsection stating it plainly, with the caveat retained that no public
source says it and none of this is silicon. Also documents the idiom that the
discarded word is free real estate for a constant.

This substantially de-risks the bench item - it becomes a confirmation, not an
investigation.

## 2. Core vs wrapper - a source boundary we had not named

Checked the Arch B spec for `EZHB_EMER_SEL` per Eli's steer. **It is not there** -
neither variant mentions EZHB_EMER_SEL, or any EZHB_* register. §4.14 is a single
paragraph and the spec carries no register map. The .sv is the same: `exec()`
takes `emergency_in` as a **bit input** and `emergency_vector` as a plain value;
no select register is modelled.

The reason is structural, and it explains more than this one question:

- **Core-level sources** (Arch B spec, sv_tb) describe the EZH engine: pipeline,
  ALU, flags, bit-slices, instruction semantics. They speak of an *emergency
  input signal*, an *external condition input*, a *breakpoint address fed from
  the system* - never the registers driving them.
- **Wrapper-level sources** (decks, AN14650, per-chip RMs) describe the NXP
  peripheral wrapper: the `EZHB_*` block, base addresses, INPUTMUX, pinmux, NVIC
  wiring, pending trap.

So the spec *cannot* settle EMER_SEL[8] polarity, and neither can hardware
analysis. Its `resolve_by` is corrected from "bench" to "per-chip Reference
Manual (nxp-monke) or bench - documentation archaeology on core-level sources
cannot settle it".

Recorded as a reader-facing note in the arm-ezh section too, because it answers
the question "why doesn't the architecture document describe these registers?"
and tells a reader which source to reach for.

**Triage consequence for the open-questions list:** items split by which side of
the boundary they sit on. Core-side questions (rshift >=32, TIGHT_LOOP corner
cases, CFS-pointer reads, STR post-update, MEM_REG offset, HOLD replica, ANDOR
width, PC read) are answerable from spec/sv/bench. Wrapper-side questions
(EMER_SEL[8] polarity, E_INT_TRIGGER(0) routing, EZH-runs-while-Arm-halted,
TxEV/__SEV) need an RM or bench and should be routed to nxp-monke alongside the
platform-guide work rather than waiting on creator review.

## Method note

The first corpus survey was wrong in a way that looked plausible (61/116 = "many
samples", matching the prior). Keil `MACRO`/`MEND` blocks and C `#define` bodies
inside a function body are not executed code. Any future corpus mining -
including the `sample-mining` step - must strip both before reading "the first
instruction".
