# Log: assembler-guide

# GOTO byte-vs-word question settled: bunny_build is correct, 2 MB is the mask

Review challenged the assembler guide's 2 MB claim, arguing bunny_build shifts a
BYTE address by 9 while goto.toml models a WORD immediate at [31:11], so either
(1) bunny_build's label branches are wrong by 4x, or (2) the 2 MB window is a
hardware property and the recorded "improvement" would break every program.
Neither. There was a third possibility not enumerated.

## The arithmetic

bunny_build: `instr = 0x15 + (1<<9) + ((byte_addr & 0x1FFFFF) << 9)`
goto.toml:   `imm = instr[31:11]; target = (PC & 0xff800000) | (imm << 2)`

A **word-aligned** byte address has bits [1:0] clear, so shifting it left by 9
places bits [20:2] - the word index - at instruction bits [29:11], which is
inside the [31:11] immediate field. Decoding `imm << 2` recovers the byte
address exactly. The `<<9`-with-a-byte-address and `<<11`-with-a-word-address
formulations are the same operation; the shift absorbs the byte/word conversion.
That is what made it look wrong.

Round-tripped bunny_build's encoder through goto.toml's decoder:

| label address | encoded    | decoded    |        |
|---------------|------------|------------|--------|
| 0x20000000    | 0x00000215 | 0x20000000 | exact  |
| 0x20000100    | 0x00020215 | 0x20000100 | exact  |
| 0x2000ABCC    | 0x01579A15 | 0x2000ABCC | exact  |
| 0x201FFFFC    | 0x3FFFFA15 | 0x201FFFFC | exact  |
| 0x20200000    | 0x00000215 | 0x20000000 | alias  |

Exact below 2 MB, aliasing above. So:

- **bunny_build is correct** within its range - no 4x defect.
- **The 2 MB limit is the mask**, not a hardware property.
- **Widening is safe**: checked all 524288 word addresses in [0, 2MB) - changing
  the mask to 0x7FFFFF alters **zero** encodings. Existing programs assemble
  byte-for-byte identically. It is an enhancement, not a bug fix, exactly as
  goto.toml recorded.
- No carry collision: the `+ (1<<9)` form bit cannot be disturbed by the shifted
  address because word-aligned addresses have bits [1:0] clear (verified over a
  4 KB span).

Chapter updated to state the range limit *and* why the encoding is nonetheless
correct - the shift is precisely the thing a reader will otherwise flag as a bug,
so it is now explained rather than left to be re-derived. The `[[unverified]]`
entry moves to status `resolved` with the round-trip recorded.

## Review's coverage concern - narrower than stated, still real

The claim was that the camera byte-for-byte anchor "never exercises label
relocation". It does: `test/ezh_apps/camera_reference_test.c` uses `E_LABEL`
five times with `E_GOSUB("PCLK_0")`, `E_GOSUB("VSYNC_0")`, `E_GOSUB("HSYNC_0")`.
So the label machinery - the thing bunny_build exists for - is covered.

But `E_GOSUB` encodes `0x3 + resolved_address`, a full absolute address with **no
mask**. The `0x1FFFFF` masked-immediate path belongs to `E_GOTO`/`E_GOTOL`/
`E_COND_GOTO`/`E_COND_GOTOL`, and *that* path is not exercised by the
byte-for-byte test. Narrower than "no label relocation", and now moot for
correctness since the encoding is settled by construction - but it is a genuine
coverage gap worth closing when a GOTO-bearing reference program exists.
`test/mcx947__ezh_goto` appears to be exactly that, on hardware rather than
byte-for-byte.

## Other review points

- **Slice-7 wording** reconciled. The assembler guide said "none of them is
  routed to the logical combiner", which contradicted the architecture chapter's
  note that slice 7's result always reaches the combiner. Rewritten so the
  conclusion does not depend on which reading is right: every slice *value* is
  zero, so the combiner sees zero either way. More robust than the original.
- **E_LOAD_32IMM guard** documented: it prints an error for a destination above
  R7 and then emits the sequence anyway - same shape as the undefined-label
  gotcha, now sitting next to it.
- **Four sites, not one**: the 0x1FFFFF mask appears in E_GOTO, E_GOTOL,
  E_COND_GOTO and E_COND_GOTOL. The chapter and the unverified entry now say so.
