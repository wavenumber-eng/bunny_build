## The probe term differs by family - this is the naming split, in the silicon

Searching `nxp-mcuxpresso` device repos:

| Repo | Probe | Result |
|---|---|---|
| `mcux-devices-mcx` | `FSL_FEATURE_SOC_SMARTDMA_COUNT` | 34+ parts |
| `mcux-devices-rt` | `FSL_FEATURE_SOC_SMARTDMA_COUNT` | MIMXRT533S, MIMXRT555S, MIMXRT595S |
| `mcux-devices-lpc` | `FSL_FEATURE_SOC_SMARTDMA_COUNT` | **0 hits** |
| `mcux-devices-lpc` | `EZH_ARCH_B` | LPC5534, LPC5536, LPC55S36, LPC55S69 |
| `mcux-devices-lpc` | `EZH` (generic) | + LPC55S06, LPC55S16, LPC54608, LPC54628, LPC54S018(M) |

**A SmartDMA-only probe silently misses every LPC part.** This is the
`[glossary.naming]` convention (logged as `naming-convention-smartdma`) showing
up as a concrete tooling hazard, not just an editorial preference: LPC-era
silicon is named EZH, MCX/RT-era silicon is named SmartDMA.

Also note `MIMXRT595S` has both `_cm33_features.h` and `_dsp_features.h` - the
DSP core sees it too. And LPC54608/54628/54S018 appear only under the generic
`EZH` probe and may be INPUTMUX references rather than real instances; needs
confirmation, and they are not in AN14650's table.

## Confirmed data sources per field

| Field | Source | Note |
|---|---|---|
| Presence | `<PART>_features.h` | `FSL_FEATURE_SOC_SMARTDMA_COUNT`; LPC needs the EZH probe |
| IRQ number | `<PART>_COMMON.h` IRQn enum | authoritative; config-tool table is 1-based, do not use |
| Base address | `<PART>_COMMON.h` | gives secure AND non-secure aliases; AN lists only NS |
| Pin mux | nxp-monkey `signal_configuration.json` | |
| INPUTMUX triggers | nxp-monkey `INPUTMUX0.json` | enumerated values present |
| Register block | nxp-monkey `SMARTDMA0.json` | field names/widths |
| Board pin wiring | Zephyr board DTS | e.g. `boards/nxp/frdm_mcxa577` |

## Durable tool - specification

Per Eli, this must not be one-off exploration. Proposed
`isa/tools/discover_parts.py` (name TBD), deterministic and re-runnable, with a
design doc under `docs/design/` in the same style as the generator:

**Stage 1 - discover.** Probe the device repos with BOTH terms; emit a candidate
part list. Records which probe matched, so LPC/MCX naming is explicit in the
output rather than implicit.

**Stage 2 - confirm and extract.** For each candidate, read `<PART>_features.h`
(presence + count) and `<PART>_COMMON.h` (IRQn, base S/NS) at the **pinned
manifest revision** from `submanifests/devices/{LPC,MCX,RT}.yml`. Pinning is what
makes regeneration reproducible and makes "what changed since last time" a real
question.

**Stage 3 - enrich (work backwards, per Eli).** Take the confirmed list and drive
`nxp-monkey` only for those parts, pulling pin mux, INPUTMUX and register-block
detail. This is the expensive stage (~134 MB/part), so it runs last and only over
parts that survived stage 2 - not over the whole catalogue.

**Stage 4 - emit.** One deterministic JSON per part, committed, stamped with tool
version + manifest revision + MCUXpresso tool version. Feeds the platform-guide
chapter generator, so the chapter is generated from data like the instruction
reference is - not hand-transcribed.

**Also needs a `--check` mode**, matching the doc generator's: re-run, diff
against committed output, fail on drift. That is what makes it a maintenance
tool rather than a one-time script - new parts appear and NXP revises headers.

## Why this matters beyond convenience

Three real errors have already been caught in this area within one session: the
IRQ off-by-one, the MCXA1xx over-generalization, and the SmartDMA-only probe
missing all LPC parts. All three came from reading a source by hand. A tool that
derives the table mechanically removes that whole class.
