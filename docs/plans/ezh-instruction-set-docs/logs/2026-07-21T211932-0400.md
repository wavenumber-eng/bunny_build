# Log: verify-encodings — SV corroboration and the ANDOR correction

Follow-up to session 1's question: can the sv_tb (advisory-only) corroborate
the 9 uncompilable fsl macros? Yes — and it caught a real DB interpretation
error that numeric probing structurally cannot see. Review approved; applied.

## The ANDOR correction (andor.toml, fields.toml)

The DB typed E_ANDOR's fourth operand as `shift5` — a 5-bit rotate amount at
[28:24] — with "mask, rotate, OR" prose. Two sources independently contradict
that:

- sv_tb `e_andor`: `result = (src1 & src2) | src3`, with `extract_src3()`
  masking 3 bits at [26:24]. Three registers, no rotate.
- AN14650 §5.9 (public, verified in the PDF): "perform both AND and OR
  operations on two register values together with a third… useful for
  simultaneously setting and clearing specific bits"; argument list
  `Flag, DST, Rsrc, Rand, Ror`; options list has ONLY conditional-execution
  and set-flag — while §5.10 immediately below spells out shift-by-imm-0-31
  explicitly.

the header author's argument name `ror` reads register-to-OR, not rotate-right. Applied:
new `or_reg3` field (3-bit register, [26:24], sv_tb-aligned, parallel to
rshift3), operand retyped, prose rewritten with the correction dated, cycles
"tbd" -> "1" (AN14650 summary table row 9, page 31, verified), restrictions
added from §5.9 (no SPO/SNE; PC-dest schedules branch instead of flags —
same wording as MOV). Bits [28:27] become reserved-zero.

**Why probing missed it**: both headers emit `ror<<24` unmasked and the
matchers compare only DB-declared value bits, so 5-bit-rotate and
3-bit-register typings both verify green. First live instance of the
pipeline's known blind class (meaning, not placement) — the SV/AN14650 layer
exists precisely for this. All three verifiers pass before AND after the
retype; only the provenance record distinguishes the readings.

## Corroboration recorded as sv_tb provenance (all marked ADVISORY)

- andor.toml: as above.
- modify_gpo_byte.toml: e_gpo_mod decodes AND [15:8] / OR [23:16] /
  XOR [31:24], low byte of GPO only (upper 24 bits pass through) — matches
  the repaired macro and AN14650 §5.14 ("Clearing and toggling GPO bottom
  byte"); cycles -> "1" (summary table row 14, verified).
- hold.toml: e_boolean decodes plain-HOLD via bit 15, NRA bit 18, LV bit 19,
  ACC bit 9, acceleration bits [31:24]; table register read ONLY from
  [23:20] — the [13:10] replica is never consumed. Prose fix: LV = large
  vector (16- vs 4-byte table stride, per SV stride logic and the fsl
  header's own "Large Vector Versions" comments) — it previously said
  "latches the vector inputs", which nothing supports.

Attribution note (review raised, resolved with evidence): the SV corroborates
NRA *semantics*, not just the bit position — `e_boolean`'s tail writes RA
(`write_that_reg(15, …)`) only under `extract_misc0() == 0`, i.e. the RA
backup is skipped when NRA is set.
