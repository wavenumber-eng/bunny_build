## Deliverable

`docs_src/cookbook.md` - 12 sections, ~2.7k words. Structure follows what a
reader arrives wanting to build rather than the instruction set's shape:

boot preamble / signal-and-park / multi-app dispatch / parameters-fresh-per-run /

Each pattern cites how common it is in the corpus, and the chapter opens by

**exactly one** worked example each - so a reader attempting them knows they are
near the edge of prior art.

## What the two under-read corpora contributed

**gibbon-d** supplied the multi-app dispatch pattern, which nothing in ezh-old
demonstrates: a shared `ezh_ram` pool, `ezh_app_offset[]` recording where each
program landed, sequential `bunny_build()` calls accumulating `last_idx`, and
dispatch by pointing `EZHB_BOOT` at an offset. Notably there is **no resident
dispatcher program** - each app is independently assembled and independently
booted. It also supplied the SPI PSRAM command-structure pattern (byte-level
subroutine inside a transaction loop, command/address/payload through the
parameter block).

**avc** supplied the continuous-capture path and a useful contrast on
`E_INT_TRIGGER`: it uses `E_INT_TRIGGER(0xFFFFFF)` - all 24 channels - where the
terminator idiom uses 0. Both are legal; the argument selects hijack channels
while the common interrupt fires regardless.

**avc also evidences Eli's descriptor aside.** `avc_camera__prepare_frame(buffer)`
re-boots the frame program per frame with a fresh buffer pointer, rather than
building a descriptor chain once. That is the boot-with-parameters model, now
with a worked example behind it rather than my unverified inference - see log
`dma-note-attribution-corrected` for why that distinction was being tracked. The
chapter states it as an observed property of the corpus, with the trade-off
(no hardware scatter-gather; full run-time freedom) rather than as a claim about
what Eli meant.

## Linter defect: silent block mis-pairing

The PC-relative report covered `architecture.md` and skipped the other two
chapters while still reporting success. Cause: `pc_report` extracted code blocks
with `^```\n(.*?)^```` , which pairs **bare** fences only. As soon as a document
also uses a tagged fence (```c), the pairing shifts - a bare opening matches the
*closing* fence of a tagged block - and every subsequent block is mis-cut or
skipped. architecture.md has 0 tagged fences and worked; assembler has 10 and
cookbook 3, and both silently reported nothing.

Replaced with a line-by-line scanner that tracks fence state and accepts tagged
fences. Verified by completeness rather than by eyeballing: grep finds exactly 2
PC-relative lines in cookbook.md, and the linter now resolves exactly 2, both
correct (+4 instructions, landing past a one-instruction loop body in each case).

**Third instance this session of a check that silently did nothing** - after the
opt-in `--pc` report and my own botched uppercase negative test. The pattern is
consistent: a check that cannot fail is indistinguishable from a check that
passes, and only completeness comparison catches it. Worth a standing habit:
after adding a check, confirm it *sees* what it should see, not just that it
does not complain.

## Method note

An inline `python -c` probe containing a fence regex returned a false negative
because **PowerShell treats the backtick as its escape character**, mangling the
pattern before Python saw it. Re-ran from a script file, which is the reliable
way to test anything containing backticks, quotes, or here-doc syntax on this
platform. Same family as the earlier PowerShell here-string failure and the
dropped line in the `--verbose` pipeline.
