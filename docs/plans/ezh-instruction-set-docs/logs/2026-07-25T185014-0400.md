## What the source actually says

Reading `src/bunny_build.c`, `src/bunny_build__instr.c` and
`src/bunny_build__psuedo_instr.c` settled several things the plan step listed
only by name:

- **Two-pass mechanics**: `pass_num == 0` counts and records labels and writes
  nothing; `pass_num == 1` emits. `idx` resets between. The invariant that makes
  it work is that *every* instruction function emits in both passes - the
  label-taking branches emit a placeholder zero in pass 0 specifically to keep
  the index advancing, with a source comment saying so.
- **Relocation**: `bunny_build()` passes the array's own address as the base;
  `bunny_build__relocate()` takes it separately. That is what allows host
  assembly for a target address, and what makes the byte-for-byte camera test
  possible.
- **E_DCD is a deprecated stub** that emits zero and prints
  "NOT YET IMPLEMENTED" on pass 1 - deliberately kept to catch ported Keil-era
  code. `E_DCD_VAL` is the working one.

## The park pattern, decoded

The plan called `E__END` "the important park pattern" without saying what it
does. It builds `CFM = 0xDB6DB600` from three shifted immediate loads and two
XORs, then holds:

    R0 = 0xDB000000
    R1 = 0x006D0000   ->  R0^R1 = 0xDB6D0000
    R2 = 0x0000B600   ->  CFM   = 0xDB6DB600

`CFM[7:0] = 0x00` clears every OR-enable. `CFM[31:8] = 0xDB6DB6` is binary `110`
repeated eight times, and `110` = 6 = `BS_0`, "always 0". So all eight slices are
forced to constant zero and none is routed to the combiner: the LC output can
never go high, `BS` can never assert, and the `E_HOLD` never releases. The core
stops fetching entirely - which is the point, since a spin loop would keep
consuming AHB bandwidth. The trailing `E_GOTO` back to the label is a safety net.

The odd-looking constants are three bytes of a repeating three-bit pattern,
chosen because that is what can be assembled from 11-bit immediates without
touching the stack.

**Correction to an earlier claim of mine**: I said the park pattern "rests on the
E_INT_TRIGGER(0) resolution". It does not - `E__END` raises no interrupt at all.
Signalling the Arm is a separate, caller's-choice step that historical samples do
*before* parking. The chapter says so explicitly. The E_INT_TRIGGER(0)
resolution is still what makes that separate step documentable, but the park
itself never depended on it.

## Two bunny_build defects found while documenting

1. **The park pseudo-instruction cannot be called under either spelling.**
   `include/bunny_build__psuedo_instr.h` declares `void E_END();`;
   `src/bunny_build__psuedo_instr.c` defines `void E__END()`. Nothing in the
   repository calls either, so the mismatch has never been exercised: `E_END()`
   fails to link, `E__END()` has no prototype in the public header. Recorded as
   `[[unverified]]` id `e-end-name-mismatch`, status open, resolve_by = code fix.
   The chapter tells readers to write the sequence inline meanwhile, and lists
   it in full.

2. **`E_GOTO` to a label reaches 2 MB, not the architecture's 8 MB.**
   `src/bunny_build__instr.c` masks the resolved byte address with `0x1FFFFF` and
   shifts left 9, filling instruction bits [29:11]; the architecture's field is
   21 bits at [31:11] covering target bits [22:2]. Already recorded in
   `goto.toml` as an assembler improvement opportunity - now surfaced to readers
   too, since it is a real difference between what the assembler emits and what
   the instruction can encode. Status `corroborated`, harmless today because EZH
   program memory sits well inside the low 2 MB on every part in the corpus.

Also documented as a gotcha, not a defect: an **undefined label does not stop the
build** - the branch prints an error and emits a zero word, which decodes as a
valid `E_MOV` rather than trapping. The program assembles, runs, and misbehaves.

## Linter earned its keep immediately

First run on the new chapter produced two real errors: `{#park}` was a `###`
subsection, so it was invisible to the section scan, which made both its
`[[provenance]]` entry and an intra-page link to it look broken.

Fixed both ways - promoted the park pattern to a top-level section (it deserves
one; it is a named plan deliverable), and corrected the linter to collect anchors
from any heading level for link resolution while still requiring provenance only
for top-level sections. A `###` anchor is a legitimate link target and the old
behaviour would have rejected it in any future chapter.

Negative-tested the corrected anchor check, twice - my first attempt used an
uppercase anchor name the regex does not match, so it proved nothing. Re-tested
with a lowercase bogus anchor and a plausible-but-missing section: both detected.

`E_END` added to the linter's non-mnemonic allow-list with its reason, since the
chapter deliberately cites the spelling that does not work.
