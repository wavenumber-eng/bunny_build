# Log: source authority ranking set (spec > AN); CFS restriction corrected; EMER_SEL resolved via nxp-monkey

Three Eli directives this session, all with substantive consequences.

## 1. Authority ranking: the creator's spec outranks AN14650

Recorded durably in `arch.toml [sources]` rather than applied ad hoc. The key
distinction captured there: **this is an authority ranking, not a citation
ranking.** The spec stays NXP-confidential - unquotable, unrenderable, never
named in output. AN14650 remains THE citable source and supplies every rendered
citation. What changes is which one wins on *what is true*.

Notes added to all three affected source entries:

- `spec_b_06` - AUTHORITY #1 FOR BEHAVIOR. Caveats recorded: core-level only (no
  EZHB_* wrapper registers), and internally inconsistent in places (its DFETCH
  chapter contradicts its own E_LDR section on write-stall), so a traced worked
  example still beats a prose sentence.
- `an14650` - ranked below the spec for behavior; known defects enumerated
  (SPO/SNE bullet contradicts its own example; EZH_SetEmergencyMode listing
  contradicts its own register table; flag table omits NZ). Still authoritative
  for the EZHB_* wrapper, which the spec does not cover.
- `sv_tb` - DEMOTED for behavior. It was an experiment; authoritative only where
  the spec is silent or self-contradictory. Still valuable for questions no
  prose source addresses (pipeline mechanics, PC arithmetic, dispatch geometry).

## 2. The ranking immediately flipped a db conclusion

Eli's steer sent me to the spec's instruction chapter, which I had skipped
because the ISA db already covered instruction semantics. Its revision history
flags "0.5 - Added CFS restrictions for LDR opcodes" - one of our open items.

The spec states, in BOTH the E_LDR and E_LDR_REG restriction lists:

> CFS bottom 8 bits will be 0x00 if CFS is used as pointer for a read

That agrees with AN14650 and contradicts hardware analysis. `ldr.toml` and
`mem_reg.toml` both carried "tentatively resolved toward the latter
[sv_tb] per source ranking" - which was correct under the OLD ranking and is
wrong under the new one. **Both corrected to resolve toward 0x00**, on the basis
that the creator's own document plus an independent public source outrank an
advisory testbench. Rev 0.5 existing solely to add this restriction is strong
evidence it was a deliberate, known behavior.

This is exactly the class of error the ranking directive was meant to catch, and
it was live in the database.

Validators re-run clean: validate.py all forms OK, verify_encodings 1492/1492,
expand_mnemonics 1502/1502.

## 3. nxp-monkey resolves the wrapper-side questions

Per Eli: fetch MCXN947 (EZH = SmartDMA there) via the `nxp-monkey` CLI. Fetched
463 files / 134 MB into the scratchpad. The tree carries, machine-readably:

- `registers/SMARTDMA0.json` - the EZHB block, 11 registers at 0x20..0x48,
  with official field names and widths
- `resource_tables/interrupts.json` - `SMARTDMA_IRQn` = **IRQ 54** on MCXN947
- `registers/INPUTMUX0.json` - `SMARTDMAARCHB_INMUX[n]`, field `INP[6:0]`,
  reset 0x7F, **with the full enumerated trigger table** (every input value
  mapped to its source: FlexIO interrupt, GPIO P0_n, ...)
- `signal_configuration.json` - `SMARTDMA_PIO` pin mux options
- SYSCON0 / AHBSC also reference SmartDMA (clock/reset, bus priority)

**EMER_SEL[8] resolved.** The field is named **`EN`**, with `RQ` at bit 9. So
AN14650's register table is right and its own `EZH_SetEmergencyMode` listing is
the inverted one - write 1 to enable. Downgraded from an open contradiction to
an inference-level caveat: the vendor data gives names and descriptions but no
enumerated values for this field, so active-high comes from NXP's naming
convention. That convention is self-evidencing in the same block - inverted-sense
bits are named negatively (`ERRDIS` = "Error Disable") while `EN`/`START`/`RQ`/
`BUFEN`/`SYNCEN` are positive.

Registered `nxp_chipdata` as a new **public** source in arch.toml - this is the
RM-grounding the plan's strategy note calls for, and it is citable. Its caveat
(enums present for some fields, absent for others; infer polarity from naming
and mark it as inference) is recorded in the source note.

Chapter updated: the EZHB register table now carries NXP's own field names
(BOOTADR.ADDR[31:2] - so 4-byte alignment is structural, not conventional;
CTRL START/EXF/ERRDIS/BUFEN/SYNCEN/WKEY; EMER_SEL EN/RQ; ARM2EZH IE/GP; PENDTRAP
STATUS/POL/EN), plus the note that the peripheral is `SMARTDMA0` on MCX and its
inputmux is literally named `SMARTDMAARCHB_INMUX` - "Arch B" in the silicon's
own register naming.
