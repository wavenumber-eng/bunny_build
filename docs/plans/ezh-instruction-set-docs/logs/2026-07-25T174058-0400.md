# Three review follow-ups completed

## 1. ALU semantic gap closed - and it generalised

The review flagged that the db recorded the SPO/SNE cancellation rule but never
said which operand survives. Investigating it produced a cleaner result than
just patching `add.toml`: **the two shift families behave differently, and one
rule explains both.**

`shift.toml` already stated "the shifted value is the LEFT operand, which
matters for SUB/SBC". `add.toml` is `dest = src1 + src2`, so src1 is its left
operand. Cross-checking against the two authoritative worked examples:

- Pre-shift, AN14650: `E_COND_LSL_ORS(SPO, R0, R0, R1, 31)` with SPO set yields
  `R1 << 31` - the *shifted* register survives, not the ALU operand.
- Post-shift, spec: `E_COND_ADDN_LSL(SPO,R1,R2,R3,24)` yields R2 inverted and
  shifted - *src1* survives.

Both are the same rule: **cancelling the ALU makes it pass through its LEFT
operand**, which is the shifted value in the pre-shift family and src1 in the
post-shift family. Every other stage (shift in its pipeline position, N
inversion, writeback, flag setting) still runs.

Recorded canonically in `shift.toml` semantics, with the consequence spelled out
in all seven ALU family files (add, sub, adc, sbc, and, or, xor) plus a
`spec_b_06` provenance entry citing the worked example. The chapter already
carried the correct claim; it now has db backing.

## 2. PC-arithmetic evaluator: `isa/tools/pc_model.py`

One module owning the PC-relative arithmetic, with a self-test built from worked
examples whose intended results the sources state outright:

- label-table `E_ADD_IMM(Rn, PC, -4)` -> next instruction
- multiply `E_LDR(R0, PC, 7)` at word 0 -> word 9, and at word 1 -> word 10
- `E_ADD_IMMS(PC, PC, 8)` -> +4 instructions
- tight-loop `E_ADD_IMM(R1, PC, 8)` -> the instruction past the body

All five reproduce. If `PC_READ_OFFSET` is ever changed, these fail loudly
instead of the change propagating silently into prose. The module also encodes
the unit split (`imm12s` raw bytes vs `offset8s` word-scaled) in code rather than
in a comment.

`lint_chapter.py` runs the self-test as a hard check, and `--pc` resolves every
PC-relative operand in every code example to an instruction delta.

**The resolver found a bug in itself on first run**: `E_ADD_IMM(R4, PC, 2*4)`
resolved to +2.5 instructions, because the regex captured `2` from `2*4`. Fixed
with a restricted product evaluator (the sources idiomatically spell byte
constants as `N*4`), and unparseable immediates now report rather than silently
mis-resolving. All five example resolutions now correct.
