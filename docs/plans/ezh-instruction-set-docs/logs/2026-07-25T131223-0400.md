# Log: architecture-overview

# E_INT_TRIGGER(0) resolved from the spec; a chapter error corrected

Eli asked whether the .sv gave a clue. It gave a partial one; the spec gave the
answer.

## What the .sv contributed

`e_int()` executes unconditionally and applies **no constraint** to the
immediate. Its only zero-handling is:

```
if (current_inst[31:8] !== 0)   // We don't push zero as it makes it difficult to check
   int_to_expect.push_back(current_inst[31:8]);
```

That comment is about the **checker**, not the DUT: a zero on the 24-bit channel
bus is indistinguishable from idle, so the testbench declines to queue an
expectation. It is an observability note, not a hardware restriction - and it
says nothing about the common interrupt output, which that queue does not model.
Suggestive (no constraint exists at the instruction level) but not decisive.

## What the spec settled

The spec's E_INT_TRIGGER section is unambiguous:

- Purpose: triggers a single-cycle interrupt output "from the common interrupt
  output **as well as** any of the 24 interrupt out channels"
- Options: immediate chooses the channels, "**common interrupt always
  triggered**"
- **Restrictions: None**

So `E_INT_TRIGGER(0)` selects no hijack channels while the common interrupt still
fires. That is precisely the end-of-program signal, which is why the corpus uses
it. **AN14650 4.2.14's "must be a positive number greater than 0" is wrong** -
contradicted by the spec (authority #1), by AN14650's own 5.21, by the training
deck, and by every sample. It reads as advice for the hijack case, where a zero
mask would be pointless.

## Chapter error corrected

The chapter had written mechanism 1 as "asserted as the OR of all bits passed to
E_INT_TRIGGER. The argument must be non-zero." **Both halves were wrong** - the
common output does not depend on the mask at all, and there is no non-zero
requirement. That came from following AN 4.2.14 while drafting, before the
authority ranking existed. Rewritten to state that the common output always
fires and the argument selects only the additional hijack channels, with the AN
discrepancy called out so a reader who checks the AN is not confused.

`int_trigger.toml` updated: restriction reworded to say a zero mask still raises
the common interrupt and is the idiomatic end-of-program signal; spec provenance
records the contradiction and its resolution; sv_tb provenance records the
testbench-observability reading so nobody re-derives it as a constraint later.

## Bonus: defect candidate #5 confirmed

The spec's E_GOTO section, read in the same pass, contains both the descriptive
sentence ("in the case of a scheduled branch, the address backed up in RA is that
following the two instructions that don't get flushed") and the formula
("strictly speaking, RA = current PC - 4 in case of scheduled branch, and
RA = current PC + 4 in case of ordinary branch").

These contradict each other, which is what goto.toml already recorded as defect
candidate #5. The .sv sides with the **descriptive sentence** (ordinary -> PC-4,
scheduled -> PC+4, i.e. GOTO+4 and GOTO+12). So the db's tentative resolution was
correct and now has independent corroboration - and the reconciliation only works
if PC = instruction + 8, which is a further cross-check on that constant.

## Status change

`E_INT_TRIGGER(0)` moves from open to resolved. **This was the only open
architecture question blocking downstream writing** - the assembler guide's
E__END park pattern depended on it. Genuinely open questions are now three:
TxEV/__SEV monitoring, EZH-runs-while-Arm-halted (both single-deck-source,
wrapper-side), and vectored-hold dispatch latency.
