# Platform-guide method revised: SDK manifest route beats config-tool data for IRQs and presence

Follows `platform-guide-scope-note`. Eli pointed at
`github.com/nxp-mcuxpresso/mcuxsdk-manifests` (follow the manifest to chip
SDK data, for IRQs) and at the Zephyr `frdm_mcxa577` board. Both change the
method, and one of them corrects an error in the previous note.

## CORRECTION: SmartDMA IRQ on MCXN947 is 53, not 54

The previous note recorded IRQ 54 from nxp-monkey
`resource_tables/interrupts.json`. **That is wrong.** The SDK device header
`MCXN947_cm33_core0_COMMON.h` gives `SMARTDMA_IRQn = 53`.

nxp-monkey's interrupt table is **1-based**; the IRQn enum is 0-based.
Calibrated against six consecutive entries:

| nxp-monkey entry | SDK header IRQn |
|---|---|
| 51 USB0_FS | 50 |
| 52 USB0_DCD | 51 |
| 53 RTC | 52 |
| 54 SMARTDMA | **53** |
| 55 MAILBOX | 54 |
| 56 CTIMER3 | 55 |

Consistent +1 across the whole region. **The SDK device header is authoritative**
- it is what `NVIC_EnableIRQ()` actually takes. Do not read IRQ numbers out of
the config-tool table without applying the offset, and prefer not to read them
from there at all.

This is precisely the class of error that would have shipped a wrong IRQ number
for every part in the chapter.

## The manifest route (concrete path)

`mcuxsdk-manifests` / `west.yml` imports `submanifests/devices/`, which contains
exactly the families we care about: `LPC.yml`, `MCX.yml`, `RT.yml` (plus DSC,
Kinetis, Wireless, i.MX).

`MCX.yml` -> project **`mcux-devices-mcx`** (remote `nxp-mcuxpresso`), path
`mcuxsdk/devices/MCX`, pinned revision, track branch `release/26.09.00-pvw1`.

Repo layout: `MCXA/`, `MCXC/`, `MCXE/`, `MCXL/`, `MCXN/`, `MCXW/` -> per-part
directory, e.g. `MCXN/MCXN947/` containing:

- `MCXN947_cm33_core0_COMMON.h` - **IRQn enum + peripheral base addresses**
- `MCXN947_cm33_core0_features.h` - **feature macros**
- `chip.yml`, `drivers/`, `arm|gcc|iar/`, `system_*.c`

## Presence detection is now a one-line test

`<PART>_features.h` carries:

```
/* @brief SMARTDMA availability on the SoC. */
#define FSL_FEATURE_SOC_SMARTDMA_COUNT (1)
```

**This settles "which parts have EZH" mechanically**, replacing the previous
plan of ~40 nxp-monkey fetches at ~134 MB each. One small header per part.

Spot-checked, confirming Eli's recollection and finding the dividing line:

| Part | SmartDMA |
|---|---|
| MCXA577 (5xx) | yes |
| MCXA557 (5xx) | yes |
| MCXA346 (3xx) | yes |
| MCXA266 (2xx) | yes |
| **MCXA156 (1xx)** | **no** |

So MCXA2xx and up carry it; MCXA1xx does not. MCXA4xx (MCXA456/457) exists but
was not spot-checked - include it in the sweep.

Note also: **MCXA4xx and MCXA5xx do exist** (MCXA456/457/536/537/556/557/566/
567/577). The previous note said they were absent - that was true only of the
nxp-monkey index at MCUXpresso tool version 26.06, which lags the SDK repo.
Another reason to prefer the SDK route for the part list.

## Base addresses carry a TrustZone subtlety

`MCXN947_cm33_core0_COMMON.h`:

```
#define SMARTDMA0_BASE     (0x50033000u)   /* secure alias */
#define SMARTDMA0_BASE_NS  (0x40033000u)   /* non-secure alias */
```

AN14650 Table 2 lists only `0x40033000` for MCXNx4x - the non-secure alias. On
TrustZone parts the chapter must give both, or say which it is quoting. A flat
"base address" column is not sufficient.

## Revised source split for platform-guide

| Data | Best source |
|---|---|
| Which parts have SmartDMA | SDK `<PART>_features.h` feature macro |
| IRQ number | SDK `<PART>_COMMON.h` IRQn enum (**not** config-tool table) |
| Base address (incl. S/NS) | SDK `<PART>_COMMON.h` |
| Pin mux options | nxp-monkey `signal_configuration.json` |
| INPUTMUX trigger map | nxp-monkey `INPUTMUX0.json` (enumerated values) |
| Register block / field names | nxp-monkey `SMARTDMA0.json` |
| Board-level pin assignments | Zephyr board DTS (see below) |

Both sources stay in play; the SDK wins for identity/numbering, nxp-monkey wins
for the mux and pin tables it enumerates well.

## Zephyr boards as a third source

Eli also pointed at `zephyrproject-rtos/zephyr/boards/nxp/frdm_mcxa577`. Board
DTS/overlay files give *board-level* truth - which pins are actually wired to
what on a specific EVK - which neither the SDK headers nor the config-tool data
provide. Relevant for the cookbook's runnable examples more than the platform
guide's reference tables. Note nxp-monkey also fetches a `zephyr3_2` variant
tree alongside `ksdk2_0`.
