# Second-round review items fixed; "nothing outstanding" was wrong

I claimed the review was fully addressed. It was not - two items were still
open, and one of them had propagated into the new tool. Both fixed, plus the
three smaller notes.

## 1. The off-by-one, in both places

`architecture.md:494` still said the `E_ADD_IMM(R1, PC, 8)` "sits two words
before the body". It sits **three** words before it - the layout is
E_ADD_IMM / E_TIGHT_LOOP / one-shot / body. Rewritten to drop the fragile
"N words before" framing entirely in favour of the arithmetic that actually
matters: PC reads +8, the immediate adds 8, so R1 lands four instructions on,
which is the first address past a one-instruction body.

The same wrong claim had been copied into `pc_model.py`'s case comment, where it
contradicted the ASCII layout printed directly beneath it. The assertion was
right (+4 words), so the suite stayed green while the prose was wrong - which is
precisely the failure mode the tool exists to prevent. Comment corrected.

**The `--pc` resolver already refuted this claim** and nobody saw it, because the
report was opt-in. It is now **on by default** (`--quiet` suppresses), on the
reasoning that a check which has to be remembered is not a check.

## 2. Register-symbol check now exists

The one review class with no mechanical coverage. `E_PER_READ`/`E_PER_WRITE`
operands are register-address macros, and published NXP listings spell several
differently from bunny_build (`EZH_BREAKADDR` vs `EZHBREAKADDR`, `EZH_ARM2EZH`
vs `ARM2EZH`). They are not `E_*` tokens, so the mnemonic check never saw them.

`lint_chapter.py` now parses `include/ezh_arch.h` for defined symbols and fails
on any `E_PER_*` operand that is not among them, with a near-miss hint computed
by underscore-insensitive comparison. Negative-tested: reintroducing both
original typos produces two failures, one carrying
"did you mean 'EZHBREAKADDR'?".

## 3. pc_model self-test hardened

- Anchor now travels in the case tuple instead of being recovered by
  string-matching "word 1" in the description. Adding a case can no longer
  silently mis-anchor it.
- Added a distinct sixth case: a **negative** word-scaled offset
  (`E_LDR(Rd, PC, -3)` -> -1 instruction). The review correctly noted the
  original five covered only four distinct calculations - the scheduled-branch
  and tight-loop cases are the identical computation. Nothing exercised the ldr
  path in the negative direction, so a sign error there was invisible.
- Drift re-verified: `PC_READ_OFFSET` of 4 or 12 now produces 6 failures each.

## 4. rshift cross-reference - and it turned out to be the interesting family

The review flagged `rshift.toml` as a soft gap on the left-operand rule, noting
the geometry "could plausibly differ" since the shift amount comes from a
register. Checking it: rshift is the family that carries **both** geometries,
selected by the order bit - shift-then-operate (`E_RLSL_ADD`) and
operate-then-shift (`E_ADD_RLSL`) both live here.

So the surviving operand differs *within* the family: the shifted src2 for
shift-then-operate, src1 for operate-then-shift. Same left-operand rule, applied
twice. Recorded in `rshift.toml` rather than left as a bare cross-reference,
because "see the shift family" would have been actively misleading here - a
reader would take away one answer where there are two.

aside, **not** a review finding - nothing in any of the three review rounds

Everything that followed in the original version of this note - that the EZH
model is boot-with-parameters, that `EZHB_ARM2EZH` carries a fresh
parameter-block pointer per run, that this is why EZH suits variable-shape work
descriptor-based DMA handles badly - was **my inference, not Eli's claim, and is
unverified**. It is plausible: the reference boot sequence does write
`EZHB_ARM2EZH = pPara | mask` before each ignition, and programs re-read it from
the top. But whether that is what Eli meant by "DMA descriptors" is unresolved -
he may have meant NXP's SmartDMA driver descriptors, or DMA descriptors
generally.
