# Platform data pipeline documented; implementation deferred to platform-guide

Per Eli: document the method first, then defer execution until the
`platform-guide` step is picked up.

## Deliverable

`docs/design/platform-data-pipeline.html` - a design doc alongside
`isa-doc-generator.html`, same style and conventions, `data-doc-status="accepted"`.
Tag balance verified against the existing design doc.

Contents:

- **Why it exists** - the platform guide needs base address, IRQ, pin mux and
  INPUTMUX map for ~45 parts; AN14650 Table 2 covers six rows and base addresses
  only. The doc opens with the three real errors already caught in this area,
  all from reading sources by hand, as the concrete argument for deriving rather
  than transcribing.
- **The naming hazard**, called out in a red block before anything else: probes
  must use BOTH names, because a SmartDMA-only search returns zero LPC parts -
  an empty result, not an error.
- **Sources of truth per field**, split across the two upstreams, with a second
  red block warning that nxp-monkey's interrupt table is 1-based and IRQ numbers
  must come from the SDK header.
- **The manifest chain**, concretely: `west.yml` -> `submanifests/devices/*.yml`
  -> `mcux-devices-mcx` at a pinned SHA -> `MCXN/MCXN947/*_COMMON.h`.
- **Four stages** with cost characteristics, marking stage 3 (nxp-monkey enrich,
  ~6 GB) as deferred by decision and noting stages 1-2 stay runnable on demand.
- **Drift checking** via `--check`, mirroring the doc generator, with the note
  that pinning makes an SDK bump a deliberate reviewable diff.
- **Open items** deliberately left for implementation rather than guessed now.

## Open items recorded (not resolved)

- Multi-core parts generally (MCXN947 core0/core1): which core's IRQ table is
  authoritative, or record both.
- Settle the output schema before stage 3 runs - cheaper to change while no
