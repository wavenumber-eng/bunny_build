## Finding: E__END is a canonicalised NXP idiom, not a bunny_build invention

`EZH_PWMClock` and `EZH_FunctionCall` both end with, character for character,
the sequence bunny_build's `E__END()` emits:

    E_LOAD_IMM(CFS, 0)
    E_LOAD_SIMM(R0, 0xDB, 24)
    E_LOAD_SIMM(R1, 0x6D, 16)
    E_LOAD_SIMM(R2, 0xB6, 8)
    E_XOR(R0, R0, R1)
    E_XOR(CFM, R0, R2)
    E_HOLD
    E_GOTO(<label>)

So the park pattern is an established idiom from the NXP sample corpus that
bunny_build packaged as a pseudo-instruction. Worth saying in the assembler
guide, which currently presents it as bunny_build's own.

**It also confirms the signal-then-park sequencing** the assembler guide
documents: both programs issue `E_INT_TRIGGER(0)` immediately *before* entering
the park block. The interrupt and the park are separate steps, in that order,
in the original sources.

## Patterns catalogued for `pattern-library`

Grouped as the cookbook chapter would likely be structured:

**Program lifecycle**
- Boot preamble: `E_NOP` padding, `E_PER_READ(R6, ARM2EZH)`, mask mode bits with
  LSR/LSL by 2, `E_LDR(SP, R6, 0)`, then further parameter loads by word offset.
  117 of 146 programs do exactly this.
- Signal-then-park: `E_INT_TRIGGER(0)` then the CFM-forced-low `E_HOLD`.
- Run-once-and-stop vs. loop-forever.

**Event handling**
- Plain `E_HOLD` gated on a configured bit-slice (72 uses).
- Vectored hold as a dispatcher (33), including the eight-entry table discipline.
- Vectored hold as a key scanner (`EZH_ButtonBitslice`).
- Pending trap as a software-triggered vector (`EZH_PendingTrap`).

**Deterministic timing**
- `E_HEART_RYTHM_IMM` + `E_WAIT_FOR_BEAT` for edge alignment (28).
- `E_SYNCH_ALL_TO_BEAT(1)` inside a tight loop for a jitter-free output clock -
  `EZH_PWMClock` produces a square wave in three instructions.

**Data movement and conversion**
- Batched `E_LDR_POST` to keep DFETCH busy, then convert (the AN performance
  idiom, used throughout the display controller).
- Format conversion in flight: RGB565->888, ARGB->RGB, endianness flip.
- 2D/strided variants (`*_DMA_2D`).

**Subroutines**
- `E_GOSUB` + `E_GOTO_REG(RA)`, with `PUSH(RA)`/`POP(RA)` for nesting.
- gibbon-d's multi-app RAM pool with offset dispatch (not yet read closely).

**Debug**
- Register dump via stores to a known buffer, plus the breakpoint
  vector pair.
- Emergency routine.

**Algorithmic**
- Shift-and-accumulate under SPO/SNE (`EZH_ConditionFlag` - the only example).
- PDM-to-PCM decimator (`hello_pdm`): 4th-order CIC, circular buffer via SP
  bit-clear, breakpoint-vector-as-seamless-loop.

## Two idioms worth highlighting in the cookbook

**Conditional execution inside branch delay slots.** `EZH_ConditionFlag`:

    E_COND_GOTO(UNS, ne2)     // scheduled branch
    E_COND_PUSH(EX,  R0)      // runs in the shadow, if EX
    E_COND_PUSH(NEX, R1)      // runs in the shadow, if not EX

The two shadow instructions are *both* executed, but their conditions are
mutually exclusive, so exactly one push happens - a branch-free select, free of
cost, riding in slots that would otherwise be flushed. This composes two features
the architecture chapter documents separately and is a genuinely good
demonstration of why scheduled branches exist.

**EZH setting its own external flag.** The same program builds `0xC0DE` in the
top half, reads `EZH_CTRL`, masks bit 1 with a `E_LOAD_SIMMN`-built inverse, ORs
in the new value and writes it back - EZH driving the `EX`/`NEX` condition that
the Arm normally owns. Confirms AN14650's "both EZH and Arm can write EZHB_CTRL
bit 1" with working code.
