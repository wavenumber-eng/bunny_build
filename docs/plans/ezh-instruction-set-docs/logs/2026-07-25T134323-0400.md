# Review findings addressed; chapter linter built

Eli's review of `docs_src/architecture.md`: 11 findings, 3 gaps, 1 process point.
All triaged; one finding did not hold.

## Finding 1 (called blocking) does NOT hold - no chipdata re-pull needed

The review reported that the in-repo vendor header contradicts the chapter's
`ADDR[31:2]`, giving `SMARTDMA_BOOTADR_ADDR_MASK = 0xFFFFFFFF` with shift 0, and
concluded two NXP artifacts disagree. Checked directly in
`test/mcx947__ezh_goto/device/MCXN947_cm33_core0.h`:

```
#define SMARTDMA_BOOTADR_ADDR_MASK    (0xFFFFFFFCU)
#define SMARTDMA_BOOTADR_ADDR_SHIFT   (2U)
```

Mask `0xFFFFFFFC` with shift 2 IS `[31:2]`. Same for `BREAK_ADDR`, `EMER_VECT`
(both `0xFFFFFFFC`) and `ARM2EZH.GP` (`0xFFFFFFFC`, shift 2). The nxp-monkey
chipdata (offset=2 width=30) and the SDK header agree exactly. The chapter is
correct as written and no re-pull is required.

The doc comment on that macro does read "32-bit boot address, the boot address
should be 4-byte aligned", which is probably what the review picked up - but it
is prose beside a mask that says otherwise.

## Confirmed and fixed (2-8)

2. **Tight-loop prose off by one.** `E_ADD_IMM(R1, PC, 8)` lands on the
   instruction *after* the body, not two past its start. The code comment was
   right; the prose miscounted. Rewritten with the walk shown.
3. "at least seven places" -> **eight** (I added an eighth item earlier and did
   not update the count).
4. "slices 0-8" -> **0-7**.
5. **Two symbols that would not compile.** `EZH_BREAKADDR` / `EZH_ARM2EZH` are
   NXP's published spellings; `include/ezh_arch.h` defines `EZHBREAKADDR` /
   `ARM2EZH`. Corrected, and a note added that the published listings differ.
6. Open-questions table contradicted its own ordering claim - `E_INT_TRIGGER(0)`
   was marked Resolved but sat in the "first four are open" block. Moved down;
   count corrected.
7. **24 vs 32 channels** reconciled: the immediate is a 24-bit field, so 24 is
   the number that matters to code; 32 is the hardware bus width. Added as a
   callout rather than silently changing one number.
8. `E_ADD_IMM(R4, PC, 0)` example - the two lines are alternatives at one
   address, not a sequence. Made explicit.

## Hedged or grounded (9-11)

9. **Surviving operand under SPO cancellation.** The review could not ground it
   in the db and flagged it as the one unsupported semantic claim. It IS grounded
   - the worked example is the architecture spec's own, which states the result
   is R2 inverted and shifted. Kept, with the operand point made explicit and an
   in-text note that the db records the cancellation rule but not the surviving
   operand, so it is spec-grounded rather than mechanically verified. **The db gap
   is real**: `add.toml` should carry this; logged for the next db pass.
10. **Heartbeat off-by-one.** Correct catch, and self-inconsistent as written:
    reload-0 beating every cycle implies period = reload + 1, putting the quoted
    20 kHz at 19,997 Hz. Added a callout and a new `[[unverified]]` entry
    (`heartbeat-period-off-by-one`); no source gives a formula.
11. **SPO/SNE legality over-restricted.** The architecture names the illegal
    cases (holds, MOV, immediate loads, data-bus), not the legal ones. Rewritten
    so plain `E_COND_ADDS(SPO, ...)` is not implied to be illegal.

## Gaps closed

- `E_SYNCH_ALL_TO_BEAT` takes a 1-bit on/off immediate - the mode is a toggle,
  not a one-way door. Added.
- Base-address table now says plainly that it reproduces AN14650's published
  list, which predates much of the portfolio, that presence is not uniform even
  within a series (MCXA173/174/176 yes, MCXA156 no), and that TrustZone parts
  have S/NS pairs.
- **Two meanings of "base"** documented: bunny_build's
  `LPC_EZH_ARCH_B_CON_BASE` points at `EZHB_BOOT`, 0x20 into the peripheral, so
  its offsets run 0x20 below the peripheral-relative table. Verified:
  `EZHBREAKADDR = CON_BASE + 0x10` is the register the table lists at 0x30.

## Process point addressed: `isa/tools/lint_chapter.py`

The review's strongest point - nothing in the repo read the chapter, so my
"74 cross-links, 19/19 provenance, containment clean" claims were ad hoc and not
reproducible. Now a real tool, checking:

1. Front matter parses and carries required keys
2. Every `[[E_NAME]]` resolves against the expanded 1502-name set
3. Every section has provenance; no provenance/unverified entry names a missing
   section; no duplicate anchors
4. No broken intra-page anchors
5. No non-public source id in body text (reads `arch.toml` for the public flags
   rather than hardcoding)
6. Every `[[unverified]]` has a status from {open, corroborated, resolved} and
   the required fields
7. Bare `E_*` tokens that are not real mnemonics warn, with an allow-list that
   requires a reason per entry

**Negative-tested**: injected a bad cross-link, a broken anchor, a missing
status, and a renamed section - all five resulting errors were caught, and the
file lints clean after restore. Items 3, 4 and 5 of this review would have been
caught mechanically; a PC-arithmetic evaluator for 2 and 8 is a sensible
follow-up but not built.

Also per the review: `[[unverified]]` entries now carry an explicit `status`
field instead of encoding "RESOLVED 2026-07-25" inside `claim` prose, so a
generator cannot render a settled item as an open hedge. Status prose stripped
from the claim strings.
