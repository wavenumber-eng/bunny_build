Design: ISA documentation generator

Status: design accepted (ADR isa-adr-0002); implementation lands in the build-static-html plan step. Decision record: docs/isa/adr/isa-adr-0002-custom-static-html-doc-generator-driven-by-the-isa-database.md. Working spike: isa/tools/gen_docs_spike.py (stdlib-only; superseded by the generator described here).

Purpose and scope

Render the machine-readable ISA database (isa/, ADR isa-adr-0001) plus narrative Markdown chapters into the static HTML documentation set that ships in this repository. The generator is ISA-db consumer #1: everything bit-accurate on a page (encodings, field layouts, modifier matrices, mnemonic lists, timing) comes from the database, which is itself mechanically verified against the original fsl header and the bunny_build encoders. Nothing bit-accurate is ever hand-written in a page.

Inputs and outputs

InputRole
isa/ezh_b/arch.toml, fields.toml, opcodes/*.tomlAll reference content: forms, fixed bits, operand/modifier fields, mnemonic patterns, timing, restrictions, provenance.
docs_src/*.md (name TBD at implementation) Prose chapters: architecture overview, programming pattern library.
docs_src/templates/*.html.j2Jinja2 page templates.
docs_src/style.cssSingle stylesheet, inlined into every page at build time (self-contained output).

Output: docs/html/ — the instruction reference is ONE page (per direction, 2026-07-22): the index carries every base opcode as a collapsed, expandable panel inline (header: name, opcode value, mnemonic count) — no separate per-opcode pages. Deep links (index.html#mov) and search results auto-expand the target panel via a hash handler. Prose chapters remain their own pages. Fully self-contained: no CDN fonts, scripts, or images; diagrams are inline SVG. Output is deterministic (stable ordering, no timestamps) and committed to the repository.

Regeneration and drift check

uv run python isa/tools/gen_docs.py          # regenerate docs/html/
uv run python isa/tools/gen_docs.py --check  # fail if committed output is stale

--check regenerates to a temporary directory and diffs against the committed tree; any difference is a failure. It joins the existing verifier suite (validate.py, verify_encodings.py, verify_fsl.py, expand_mnemonics.py) so documentation drift fails CI exactly the way encoding drift does. Generated output is only ever committed together with a passing check.

Architecture

isa/*.toml ──▶ data layer ──▶ page model ──▶ Jinja2 templates ──▶ docs/html/
               (validate.load + derivations)         ▲
docs_src/*.md ──▶ markdown + cross-link resolution ──┘
  • Data layer — reuses the verifier modules rather than reimplementing them: validate.load() for parsing, verify_encodings.form_mask_match() for decode mask/match, expand_mnemonics.expand() for the name lists (the same code whose output is verified 1502/1502 against the fsl header). Derives the bitfield segment model per form: per-bit ownership (fixed / field / reserved-zero), merged into contiguous same-owner runs.
  • Page model — plain dicts handed to templates; no logic in templates beyond iteration and formatting.
  • Templates — Jinja2 (jinja2 dev dependency), one template per page kind plus a shared layout.
  • Prose chapters — Markdown rendered with python-markdown; [[E_NAME]] tokens resolve against the expanded mnemonic set to opcode-page links, unresolved names are build errors.

Opcode section structure (one expandable panel per opcode)

  1. Panel header: opcode name, 5-bit value, mnemonic count (collapsed by default; anchor id = opcode name).
  2. Semantics prose and restrictions (from the db, synthesized text only).
  3. Timing: cycles plus qualifying note.
  4. Per form: syntax line; derived decode mask/match; bitfield diagram with an "opcode" caption on the fixed low bits, a one-line color legend (green fixed / tinted fields / dim reserved-zero), and db-generated hover tooltips on every cell — field description, width, and slice mapping; the full 16-condition table on the cond cell; the register map on register cells; opcode identity on the fixed low bits; the reserved-zero rule on dim cells; form notes; expanded mnemonic table (name, canonical base word) — including alias mnemonics (E_POP/E_PUSH families) on their base form's section, presented as presets of that form.
  5. Public-source citations only (see Provenance).

Bitfield diagrams

Inline SVG generated from the slice data — the third emitter alongside the C and Verilog demos in validate.py. Algorithm (proved in the spike): classify each of the 32 bits as fixed (with its bit value), owned by an operand/modifier field, or reserved-zero; merge adjacent same-owner bits into segments; render one labeled cell per segment with bit indices at the segment boundaries. Fixed segments show their binary value; reserved-zero segments show 0; split fields (e.g. the PER_WRITE address) naturally render as multiple cells carrying the same field name.

Provenance rendering

Source ids come from arch.toml [sources], each flagged public. Only public sources (AN14650, bunny_build) render as citations, with section numbers where recorded. Non-public ids (spec_b_06, fsl_header, sv_tb) never appear in generated output; the prose they informed is synthesized text in the db. This enforces the plan's "synthesize, don't copy" rule at the rendering layer as well as the authoring layer.

Styling

Direction (Eli, 2026-07-22): the supply-chain-monkey status page (src/py/scm/server/templates/status.html, deployed at scm.wavenumber.net/v1/) copied verbatim where applicable: amber phosphor-glow terminal aesthetic, monospace throughout, flat collapsible panels ([-]/[+] headers), status rows, bordered result tables, the glow via text-shadow: 0 0 10px var(--amber-glow). The monkey ASCII art is replaced by the bunny from this repository's README.

  • Tokens: the SCM palette verbatim as CSS custom properties (--bg-dark #1a1a1a, --bg-panel #242424, --bg-input #2d2d2d, --border #3d3d3d, --amber #ffb000, --amber-dim #cc8800, --text #e0e0e0, --text-dim #808080, --green #00ff00, --red #ff4444), plus bitfield cell tint tokens for the SVG diagrams.
  • Themes: dark is the identity and the default. Light mode is a manual option (data-theme="light" on the root, toggled from the footer, persisted in localStorage) with a warm-paper rendering of the same amber identity. No prefers-color-scheme auto-switch — deliberate.
  • Type: monospace only, via a --font-mono token. The footer carries a font cycler (Consolas / Cascadia Code / JetBrains Mono / IBM Plex Mono / Courier) for trying options; the final stack gets pinned once chosen. Local system fonts only — no font CDNs, and the GitHub Pages target keeps the no-external-asset rule.
  • Diagrams: SVG cells styled through CSS classes over the tokens so they follow the theme; fixed-bit values render in --green, reserved-zero cells dimmed.

Hosting

Long term the generated docs/html/ tree is published with GitHub Pages (custom domain planned). The self-contained/no-CDN constraint means the committed tree is the deployable artifact as-is; Pages just serves it. Publishing workflow lands with build-static-html.

Site organization (decided 2026-07-22)

Seven top-level sections, each its own page, sharing a header bar (the bunny identity plus section navigation) and the token stylesheet; search spans all of them. (1) Home; (2) Architecture — exhaustive: all ARM/EZH interrupt mechanisms, the runs-two-ahead pipeline nuances, boolean detection, heartbeat, EZHB control block; (3) Instruction reference — the generated expandable page; (4) Assembler guide — directives and pseudo-instruction layers (E_DCD/E_DCD_VAL/E_LABEL, E_LOAD_32IMM, the E__END park pattern), the on-target assembly thesis; (5) Cookbook — patterns from the mined sample corpus; (6) Platform guide — per-chip base addresses, pin mux, IRQ numbers, INPUTMUX maps (data via nxp-monke); (7) Simulator placeholder. Sections 2-3 are machine-truth; 4-6 are the bunny_build programming world.

Search

Client-side, fully static, precomputed by the generator at build time — no backend at any point (GitHub Pages stays plain hosting). The generator already holds everything searchable in structured form; it emits one deterministic index asset and a small hand-written lookup script (SCM-styled search panel on every page, / focuses it). Three tiers, all precomputed in Python:

  1. Exact/prefix mnemonic lookup — a name → page#anchor map over all 1502 expanded mnemonics (plus register, condition, and field names). Typing E_COND_LDRB lands on the ldr page instantly. Supersedes the index-filter promise in ADR isa-adr-0002.
  2. Fuzzy matching — trigram → posting-list index built at generation time; the client intersects query trigrams and scores the candidate set (prefix > substring > trigram overlap), so vectred hold still finds the hold page.
  3. Full text — an inverted token index over prose, restrictions, and (later) architecture chapters, weighted title > mnemonic > restriction > body.

Constraints: the index ships as a JS file (<script src="search_index.js"> defining a global), not JSON via fetch() — fetch is blocked on file://, and the docs must work opened straight from disk. Output is deterministic (sorted keys, no timestamps) so --check covers the index like every page. Expected size for this corpus is tens to low-hundreds of KB. No search library: third-party engines solve large-unstructured-corpus problems; this corpus is small and its structure is ours.

Deferred

  • Client-side mnemonic filter on the index (small inline script over the name table; exact-name lookup is the common case given 1502 mnemonics).
  • Full-text search — revisit when prose volume warrants it.
  • Per-form machine-readable timing — the db carries cycles per opcode file (matching AN14650's granularity), with multi-form distinctions (NOP vs WAIT_FOR_BEAT, GOTO scheduled-vs-ordinary) in prose notes. Adequate for docs; the simulator will eventually want structured per-form cycles.
  • Simulator page (parked ezh-browser-simulator plan) — embeds later as one more static page plus a WASM asset; no toolchain interaction.
