Design: platform data pipeline

Status: method accepted (Eli, 2026-07-25); implementation deferred to the platform-guide step of the ezh-instruction-set-docs plan. Purpose: derive the per-part EZH/SmartDMA reference tables mechanically instead of transcribing them by hand. Consumer: the platform guide chapter (site section 6), generated the same way the instruction reference is — from data, not prose.

Why this exists

The platform guide needs, for every part carrying EZH/SmartDMA: base address, IRQ number, pin mux options, and the INPUTMUX trigger map. AN14650 Table 2 covers six rows and gives base addresses only; the current portfolio is roughly forty-five parts and still growing. Hand-transcription across that surface is where errors breed.

That is not hypothetical. Three separate errors were caught in this area within a single working session, every one of them from reading a source by hand:

  • An IRQ number off by one, taken from a 1-based table (see the trap below).
  • A rule — “MCXA1xx parts do not have it” — generalised from two spot checks, and wrong: MCXA173/174/176 do.
  • A discovery probe that silently returned zero LPC parts because it searched for the wrong one of the block’s two names.

A pipeline that derives the table mechanically removes that whole class of error, and makes “what changed since the last SDK release?” an answerable question rather than a re-audit.

The naming hazard (read this first)

Discovery must probe for BOTH names. The block is called EZH in LPC-era silicon and SmartDMA in MCX/RT-era silicon (see arch.toml [glossary.naming]). Searching only for FSL_FEATURE_SOC_SMARTDMA_COUNT returns zero LPC parts — not an error, just an empty result, which is the dangerous kind.

The tool must record which probe matched each part, so the LPC/MCX naming split stays explicit in the output rather than being flattened away.

Sources of truth, per field

Two upstreams, used for different things. Neither is sufficient alone.

FieldSourceNotes
Presence of the blockSDK <PART>_features.h FSL_FEATURE_SOC_SMARTDMA_COUNT; LPC needs the EZH probe instead
IRQ numberSDK <PART>_COMMON.h IRQn_Type Authoritative — it is what NVIC_EnableIRQ() takes
Base addressSDK <PART>_COMMON.h Gives secure and non-secure aliases on TrustZone parts
Pin mux optionsnxp-monkey signal_configuration.jsonSMARTDMA_PIO
INPUTMUX trigger mapnxp-monkey INPUTMUX0.json SMARTDMAARCHB_INMUX[n], INP[6:0], enumerated values present
Register block / field namesnxp-monkey SMARTDMA0.jsonOffsets, widths, field names
Board-level pin wiringZephyr board DTS e.g. boards/nxp/frdm_mcxa577; for cookbook examples rather than reference tables

Do not read IRQ numbers from the config-tool interrupt table. nxp-monkey’s resource_tables/interrupts.json numbers entries 1-based, while IRQn_Type is 0-based. Calibrated across six consecutive entries on MCXN947, the offset is a consistent +1: the table’s entry “54” is SMARTDMA_IRQn = 53. Take IRQ numbers from the SDK header.

Pin the revision. The submanifest carries an exact SHA per device repo. Reading at that SHA rather than at a moving branch is what makes regeneration reproducible and makes a diff between two runs meaningful.

Stages

1 — Discover (cheap)

Probe the three device repos with both terms; emit a candidate part list with the matching probe recorded per part. The implemented tool uses the unauthenticated GitHub tree API plus raw file fetches; GitHub code search currently requires authentication, so it is not part of the reproducible path.

2 — Confirm and extract (cheap)

For each candidate, read <PART>_features.h and <PART>_COMMON.h at the pinned revision. Yields presence, instance count, IRQ number, and base addresses (secure and non-secure). Parts that fail confirmation drop out here with a recorded reason — a part that matched a broad EZH grep because of an unrelated INPUTMUX reference must not survive into the output silently.

Stage 1–2 implementation (2026-07-28): isa/tools/discover_parts.py emits isa/ezh_b/platform/index.json plus one JSON file per confirmed part under isa/ezh_b/platform/parts/. For LPC, it also performs the broader EZH metadata sweep across feature headers, COMMON headers, chip.yml files, and EZH-named paths, then records any unconfirmed candidates, including any IRQ/base-address facts visible in the candidate COMMON header. The current run finds 57 SDK-confirmed parts across MCX and RT, with 77 core views. It records a hard open item for LPC because the pinned LPC repo has no feature header matching FSL_FEATURE_SOC_SMARTDMA_COUNT or EZH_ARCH_B, while the broad sweep finds three unconfirmed LPC55 common-header candidates.

3 — Enrich (expensive; deferred)

Drive nxp-monkey fetch for confirmed parts only, then extract pin mux, INPUTMUX triggers, and the register block. This is the “work backwards” stage: the confirmed list drives the fetches, so the catalogue is never swept wholesale. Roughly 134 MB per part, so approximately 6 GB across the current list.

Stage 3 remains deferred by decision (Eli, 2026-07-25) until the SDK-header data shape and open extraction gaps are reviewed. Stages 1–2 are cheap enough to run on demand in the meantime.

4 — Emit

One deterministic JSON per part, committed, stamped with tool version, pinned manifest revision, and MCUXpresso tool version. The static doc generator reads that committed JSON and renders the SDK-header platform view: confirmed parts, per-core IRQ/base-address facts, unconfirmed candidates, and open extraction gaps. The later enrichment pass fills in pin mux, INPUTMUX, and wrapper setup details.

Drift checking

uv run python isa/tools/discover_parts.py --self-test          # offline parser regression tests
uv run python isa/tools/discover_parts.py                      # regenerate
uv run python isa/tools/discover_parts.py --check              # fail if committed output is stale
uv run python isa/tools/discover_parts.py --require-complete   # fail on unresolved extraction gaps

Mirrors the doc generator’s --check: regenerate to a temporary tree, diff against the committed output, any difference is a failure. This is what makes the pipeline a maintenance tool rather than a one-time script — NXP adds parts and revises headers, and the failure should be loud. The discovery command runs the parser regression tests before touching network data, including zero-count EZH macros and RT-style SDMA_IRQn matching. Because the manifest revision is pinned, a bump to a newer SDK release is a deliberate, reviewable change with a visible diff.

Open items for implementation

  • The pinned LPC device repo currently has 47 feature headers but no FSL_FEATURE_SOC_SMARTDMA_COUNT or EZH_ARCH_B match. The implemented broad sweep checks feature/common/chip metadata and EZH-named paths, then records unconfirmed candidates. Legacy LPC rows therefore need AN/RM/nxp-monkey confirmation instead of silently falling out of the generated table.
  • Confirm whether LPC54608/54628/54S018(M) are genuine instances or matched the broad EZH probe via an unrelated INPUTMUX reference. They are not in AN14650’s table.
  • RT500 parts advertise FSL_FEATURE_SOC_SMARTDMA_COUNT and expose SDMA_IRQn, but their COMMON headers do not contain a SmartDMA-prefixed base-address macro. --require-complete fails on those rows until the base-address source is settled.
  • Settle the output schema before stage 3 — it is cheaper to change with no fetched data committed.

Relationship to the rest of the doc set

The platform guide does not gate build-static-html (decided 2026-07-22): the generated doc set can ship with the current SDK-header platform view while the pin mux and INPUTMUX enrichment remains active. Two open questions from the architecture chapter are wrapper-side and should be answered opportunistically during that work, since they need exactly this data: E_INT_TRIGGER(0) / interrupt-hijack routing, and confirmation of the EZHB_EMER_SEL[8] polarity inference across more than one part.
